**21:55 — fix: Cloudflare 1102 root cause, body-part split, and a false-"Applied" AI bug**
A real user hit Cloudflare Error 1102 on `/api/coach` in production. Diagnosed from Cloudflare's own Workers Observability telemetry for the exact Ray ID (`a3e38d65bc19ed14`), not guessed: `outcome: "exceededCpu"`, `cpuTimeMs: 10` (this account is on the Workers Free plan's 10ms-per-invocation ceiling), `wallTimeMs: 46` — ruling out `maxDuration` (a wall-clock concept, irrelevant here) as a factor. Root cause: several `lib/data/*.ts` functions the coach route depends on (`getActivePlan`, `getWeeklyStats`, `getCurrentStreak`, and others) independently called `requireUser()`, each constructing a fresh Supabase client and making a redundant network round-trip to re-verify a session `route.ts` had already authenticated — 3 guaranteed redundant re-auths on every single coach request before any tool even ran, more if tools were invoked. A second, compounding cost: all 14 AI tool Zod schemas were rebuilt (and re-converted to JSON Schema for Anthropic) on every request instead of once per Worker isolate. Fixed both — added `*ForUser(supabase, userId, ...)` variants of the affected data functions (originals unchanged, now thin wrappers, so every other caller is unaffected) and hoisted the tool schemas to module scope. Verified live post-deploy via real authenticated server-to-server requests to production (no functionality removed, nothing guessed).

Also implemented the `body_part` split the user explicitly wanted and the generator couldn't produce (`custom` was silently resolving 4-day requests to `upper_lower`): four new day templates (Chest & Triceps, Back & Biceps, Shoulders & Abs, Legs) cycling via the same `pattern[i % n]` mechanism `push_pull_legs` already used, wired through `SplitType`, a new migration (`0011_body_part_split.sql`, extending the `split_type`/`change_type` CHECK constraints), onboarding, settings, and a new `change_split` AI tool (propose-only, like every other plan-editing tool) — tested with 11 new Vitest cases (cycling order for 4–7 days, exercise-focus matching per day) and a live end-to-end database check of change_split's propose → apply (new plan active, old archived) → cancel (unchanged) → reload-status flow.

Separately, fixed a real trust-breaking bug: the AI could say "Applied — your plan has been updated" after only proposing a change, before the user had clicked anything. Root cause was a combination of a too-permissive system prompt and an ambiguous tool-result shape, not a UI bug — the confirmation card and server-side apply path were already correctly gated. Fix: the system prompt now has an explicit, example-driven section banning past-tense completion language after any plan-editing tool call; every such tool's result now includes an explicit `"status": "pending"` field, not just `"proposed": true`; and the confirmation card gained a fifth, `Failed` state (an apply error now shows inline and offers retry, instead of silently reverting to looking like nothing happened). Live-verified against the real deployed model: asked to switch to the body-part split, its actual response was *"I've prepared that switch — ... Take a look at the card below and hit Apply Change to make it your active plan."*

**23:21 — feat: expand exercise library, add pending-change nav indicator, narrow generation-pool queries**

Re-verified the prior pass's fixes (proposal states, the "never say Applied before Apply" system-prompt rule, the `body_part` split, `change_split`) by reading every file involved end to end — all confirmed genuinely in place, nothing needed re-fixing.

Massively expanded the exercise library: evaluated both datasets the brief named. [Free Exercise DB](https://github.com/yuhonas/free-exercise-db) is confirmed public domain (The Unlicense) via GitHub's own license-detection API, not its own self-description; [wger](https://github.com/wger-project/wger)'s exercise data is Creative Commons *per individual entry* (no blanket license), which would need real per-row license capture from its live API to use correctly — a materially larger, riskier scope addition than importing a single, unambiguously-licensed dataset. Built a reusable, idempotent ingestion pipeline (`lib/data/exercise-import/`, `scripts/import-exercises.ts`: fetch → Zod-validate → map onto WorkoutMate's own muscle/equipment/difficulty/movement-type vocabulary → dedupe by name against anything already in the table → upsert by `(source, source_id)`) and ran it for real against the production database: 853 of 876 Free Exercise DB exercises imported, 23 correctly skipped as duplicates of the existing hand-authored set. Deliberately did **not** import Free Exercise DB's images — the text data's Unlicense is confirmed at the repo level, but the README's own account of the dataset's lineage (restructured from an older, separately-sourced dataset) doesn't give the same confidence for image rights, so every imported row's `image_url`/`video_url` is left null rather than assumed clean. New migration `0012_exercise_library_expansion.sql` adds per-row `source`/`source_id`/`license`/`license_url`/`attribution`/`external_url`/`aliases`/`force` columns and a trigger-maintained, GIN-indexed `search_vector` (a generated column wasn't possible — `to_tsvector(regconfig, text)` isn't IMMUTABLE in Postgres, SQLSTATE 42P17 — discovered by trying it against the linked project, not anticipated in advance). Library is now ~930 exercises.

Rebuilt `/exercises` as a server-side paginated, filterable, searchable page (query via the new full-text index, plus muscle/equipment/difficulty/category/movement-type filters) — the old version loaded the entire table into the browser on every visit, workable at 75 rows and not at ~930. Broadened the AI coach's `replace_exercise` substitute search (`getSubstitutesForExercise`) to fall back to the same full-text index when the curated/same-muscle-same-movement-type match is thin or the user named what they wanted, instead of only ever considering a strict same-muscle match.

Added a persistent "N pending plan changes · Review" indicator (nav badge, sidebar link) driven by a new `getPendingChangeCount()` query, so a proposal card doesn't become effectively invisible if the user scrolls past it or navigates away from `/coach` — the confirmation card remains the only place that can actually Apply/Cancel.

Since three AI-tool call sites and onboarding load the full exercise pool on every plan generation, and that pool just grew ~10x on the same CPU-constrained `/api/coach` path that caused the earlier Cloudflare 1102, narrowed every such query from `select("*")` to an explicit column list matching exactly what the generation/selection logic reads (`lib/generation/pool-columns.ts`) — a direct, targeted follow-through on that incident's root cause, not new scope.

83 tests (76 + 7 new, covering the import pipeline's dataset-value mapping and its intentional skip cases), typecheck, lint, and production build all clean. **Not deployed this pass**: this session's environment was missing `.env.local` and Cloudflare/wrangler credentials (confirmed genuinely absent — reproduced on the pre-existing `db:seed` script too, not something this session's changes caused), so `cf:deploy` was deliberately not run rather than ship a build missing its public runtime config. The migration and the exercise import both still happened for real against the production database, through the Supabase CLI's own separate, unaffected authenticated session. See `docs/PROJECT_STATUS.md`'s "Deploy gap" note for exactly what's left and how to unblock it.
